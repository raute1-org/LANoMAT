# QA rulings

Product-owner decisions taken during QA round 1. Each entry records what was decided, why, and what it costs if the decision turns out wrong.

- **Ruling A (OQ-07, tournaments need an event registration).** Enrolling in a tournament and checking in to it requires the acting user to hold a non-cancelled registration (pending or confirmed) for the tournament's event. Enforced in `TournamentPolicy::enroll` / `checkIn` (so web, Discord `/tournament checkin` and Filament all share it) via `Tournaments\Support\EventRegistrationRequirement`, which only touches Registration through its public read-model `MyRegistration` and `RegistrationAvailability` (architecture baseline extended by the single edge `Tournaments -> Registration`). Orga bypasses. For team entries only the acting owner's registration is checked, not every roster member's. The tournament pages show "Melde dich zuerst zum Event an" with a link to the registration page while registration is open. *Why:* no-shows without a ticket distorted brackets and capacity. *Cost if wrong:* some legitimate guests (walk-ins registered late) are blocked until they register; relaxing means deleting the two policy clauses.
- **Ruling B (OQ-N7, withdraw own entry).** The owner of an entry (solo user, or the team owner/captain for a team entry; never a plain member) can withdraw while the tournament is in `enrollment` or `check_in` (`TournamentPolicy::withdraw`, route `tournaments.withdraw`, button with `confirm()` like registration cancel). `WithdrawEntry` now locks the parent tournament row first (same order as `EnrollSolo`/`StartTournament`), so a withdrawal racing a start either wins before seeding or is rejected as already started; it also clears `checked_in_at`. Withdrawn entries never count toward `max_entries`, so the slot is free immediately. `entryFor` (web) and the Discord check-in lookup now resolve the latest non-withdrawn entry, so withdrawing and re-enrolling works. *Why:* participants could not leave a bracket they would not play. *Cost if wrong:* late withdrawals before check-in close leave a gap an orga must fill by hand; the team "captain" is the team owner, there is no separate captain role.
- **Ruling C (OQ-N6, no self-cancel after check-in).** `RegistrationPolicy::cancel` lets a participant cancel their own registration only while `checked_in_at` is null and the event is not `finished`/`archived`; orga can always cancel. `RegistrationPolicy::cancelBlockedReason()` (`checked_in` | `event_over`) feeds both the policy and the registration page (`registration.canCancel` / `cancelBlockedReason`), where the cancel button is replaced by a short German explanation; a direct DELETE flashes the same message instead of a 403. Orga cancels through a new "Stornieren" row action on the event's registrations table (Filament had no cancel path before); `CancelRegistration` now also clears `checked_in_at` (the seat is still released by the `RegistrationCancelled` listener, event dispatch unchanged). *Why:* a checked-in guest vanishing from capacity/seating mid-LAN was unrecoverable and untraceable. *Cost if wrong:* a guest who leaves early must ask orga to cancel; clearing `checked_in_at` on cancel loses the arrival timestamp of cancelled registrations (re-register already reset it).
- **Ruling D (OQ-N2, timezone).** `app.timezone` stays UTC and no stored row changes. One display/input zone, `config('lanomat.timezone')` (env `APP_DISPLAY_TIMEZONE`, default `Europe/Berlin`), is used by: `EventDays` (arrival days, so an event starting 2026-11-20 00:30 Berlin = 23:30 UTC still offers "Fr, 20.11." first), Filament via `FilamentTimezone::set()` in `AppServiceProvider` (DateTimePickers read/write and `dateTime()` columns render in Berlin time; verified against the v5 `TimezoneManager`), schedule notification `H:i` times, and all Vue date formatting (`formatInstant`/`dayKey` in `resources/js/lib/datetime.ts`, zone from the shared Inertia prop `displayTimezone`). *Why:* UTC display/arrival days were one hour off around local midnight. *Cost if wrong:* a non-German deployment must set `APP_DISPLAY_TIMEZONE`; the arrival-plan day values already saved (plain `Y-m-d`) are unaffected. Not done / follow-up: Event::starts_at-based Discord/mail text that formats dates server-side does not exist yet (none found); any new server-side `format()` of an instant must go through `DisplayTimezone::local()`; `Event/Index.vue` formats only a year via the browser zone (immaterial).
- **Ruling E (F-01, tournament lifecycle in the admin).** A tournament is created as `draft` and the form has no status field; orga now moves it with Filament actions on the edit page (header) and the list (row), shared in `Tournaments\Filament\Support\TournamentLifecycleActions`, each delegating to an Action class that row-locks the tournament like `StartTournament`: `OpenTournamentEnrollment` (draft -> enrollment; refuses with a German list of what is missing: game, max. Anmeldungen (>= 2), and, unless `settings.require_checkin` is false, check-in opens/closes with closes after opens), `OpenCheckin` (enrollment -> check_in, now locked; the scheduler tick still does this automatically at `checkin_opens_at`), `StartTournament` (unchanged) and `ReopenToDraft` (enrollment|check_in -> draft only with zero non-withdrawn entries; the button is hidden otherwise). The edit page shows the status as a Filament badge under the title. No new states or transitions beyond draft <-> enrollment. Visibility is unchanged: draft tournaments are listed on the event's tournaments page like before (they only gate on the event's public visibility) but offer no sign-up. *Why:* participants could only enroll in `enrollment` and nothing in the admin ever set it. *Cost if wrong:* the scheduler tick can still move enrollment -> check_in on its own, so "Anmeldung schließen" can disappear without an orga click once entries exist or check-in opens.
- **Ruling F (team tournament enrollment).** The index/show enroll button for `team_size > 1` tournaments posted without `team_id` (404). The page now gets a `teamPicker` prop (`Tournaments\Support\TeamPicker`: the viewer's own teams, `eligible` = roster size equals `team_size`); the UI shows a Select + "Mit Team anmelden", disables non-eligible teams, and for users without a team shows a hint plus a link to create one. The enroll endpoint flashes a German error instead of a 404 when `team_id` is missing. Authorization is unchanged (`TeamPolicy::update` + `enroll` policy). *Cost if wrong:* team admins who are not the owner (orga bypass of `update` aside) cannot enroll a team they do not own; there is no captain role.

- **Ruling G (F-S4-1/2/3/8/9/13, result reports).** The participant form keeps the wording "Ergebnis (du) : Ergebnis (Gegner)"; `SubmitMatchReport` now takes `ownScore`/`opponentScore` and stores the report entry-oriented (`score1` = entry 1) by the reporter's side, so an entry-2 reporter no longer credits the opponent and confirm crowns the claimed winner. The tournament page gets a `pendingReports` prop (`Support\PendingReportView`, participants only, from the viewer's perspective: own/opponent score, who reported, when); the card shows it to both sides, the reporter sees "Warte auf Bestätigung durch <Gegner>" instead of Bestätigen/Anfechten, 422s render inline, match numbers show `position` (positions were already 1-based). The disputes table shows the claimed score ("Anm. 1 : Anm. 2"), reporter and time. A repeated confirm/dispute click by a participant redirects with an info flash ("Diese Meldung wurde bereits bearbeitet.") instead of a 404; two existing tests that asserted 404 for that case now assert the redirect (a match without any report, or a non-participant, still 404s). Helper "Go" flashes a success toast. Not done: reporter withdraw/correct of a pending report (the domain has no such transition: it would need a new Action, status and policy); follow-up. Non-entered withdraw still answers 404. *Why:* wrong winners were crowned without anyone seeing the claimed score. *Cost if wrong:* the stored `match_reports` rows keep entry orientation, so any future consumer must not assume "reporter first"; orientation is documented on the Action.
- **Ruling H (F-S4-4/5/12, completion and standings).** A tournament is finished when its decisive match is decided: single/double elimination with two entrants (one match, no `nextMatch`) now finishes (the early exit only meant to exempt round robin is replaced by an explicit format branch). Round robin finishes when every match is decided; standings come from the pure `Domain\RoundRobinStandings`: wins, then score difference, then head-to-head only for an exact two-way tie, then points scored, then lowest entry id as a stable order (entries still level on all of the first four share a rank); the winner is the first row. The tournament page shows the table (all states; no cell-level loading state since Inertia reloads in place) and a "Sieger" line for any finished tournament; the admin edit page lists the table as read-only text lines (Filament-native). The unused grand-final reset shows "Entfällt" once the tournament is finished and bye/phantom cards print no scores. *Why:* RR and n=2 hung in Live forever. *Cost if wrong:* a different tiebreak order (e.g. mini-table for 3-way ties) changes only `RoundRobinStandings` and its tests.
- **Ruling I (F-S4-6/7, start and check-in guards).** Every format refuses to start with fewer than 2 participating entries (checked-in ones when check-in is required) via German `TournamentException::notEnoughEntries`; single elimination above 64 is refused like double elimination (the module documents 2..64). The Filament start action shows these as a danger notification. The scheduler tick skips tournaments with fewer than 2 participating entries and logs one warning per tournament per 6 hours (cache marker), `StartTournamentJob` logs and finishes (no retry, no `failed_jobs` row) on a rule refusal. Manual "Zur Check-in-Phase" sets `checkin_opens_at = now()` when it lies in the future, and refuses with a German message when `checkin_closes_at` has already passed; the tournament form validates closes after opens. *Why:* the button showed but check-in was refused, and an under-filled tournament filled `failed_jobs` every minute. *Cost if wrong:* orga loses the originally planned check-in opening time when opening early (it is overwritten); the 6 h log window can hide a recurring problem for that long.
- **Ruling J (F-S4-11, index).** The index shows "x / max Anmeldungen" (or "Teams" for `team_size > 1`) plus "ausgebucht" while enrollment is open and full, and sorts live, check-in, enrollment, draft, finished (ties by `starts_at`). Withdrawn entries do not count. *Cost if wrong:* a pure sort-key change in the controller.
- **Ruling K (F-S6-1/2/3, realtime).** All `ShouldBroadcast` events use `App\Support\Broadcasting\RetriesBroadcast` (`tries = 3`, `backoff = [2, 10]`; a test enumerates every broadcast event so new ones cannot forget it), so a short Reverb restart no longer loses a push. New `MatchReportUpdated` (`match.report_updated`, ids and status only, no scores) is dispatched on submit and dispute; the tournament page listens to it and to `tournament.started`. The client `useResync` composable reloads the live props (`matches`, `tournament`, `pendingReports`, `standings`; presence page: `presence`) when the socket reconnects after a drop and when a hidden tab becomes visible again (throttled to one reload per 5 s). The LIVE badge keeps meaning tournament status; a calm warn indicator "Verbindung unterbrochen" appears next to it only while the socket is down. There is no JS unit-test runner in the repo, so the client logic is verified manually in the browser (see the QA notes), the PHP side by tests. *Why:* clients that missed a signal stayed stale until the next unrelated broadcast. *Cost if wrong:* up to 3 delayed duplicate broadcasts during an outage (harmless: clients reload on each); a reload on every tab focus costs one cheap partial request.
- **Ruling L (F-S4-13, panel copy).** Filament's formal ("Sie") German strings that the panel actually shows (modal confirmation, throttle notice, unsaved-changes alert, error notification, select/mention prompts, empty notification text) are overridden with "du" via `lang/vendor/filament-*/de` (partial overrides, merged by Laravel over the package files). The login/MFA/export strings are not overridden because the panel uses Discord-only login and no MFA. *Cost if wrong:* a Filament upgrade that renames keys leaves the override dead (the formal text returns); `FilamentDuCopyTest` fails when a key stops resolving.
- **Ruling M (F-S2-2, bell).** `unreadNotifications` (list, 15) and the new `unreadNotificationCount` are plain closure props, no longer `Inertia::optional`, so every response (including the redirect after "Als gelesen markieren" or any other POST) carries them; `NotificationBell` reads both and no longer reloads on mount. The badge shows the real count (99+ cap). *Why:* an optional prop is dropped from a redirect, which emptied the bell although notifications were unread. *Cost if wrong:* two small indexed queries per authenticated request; partial reloads that do not name the props keep the previous values until the next full visit.
- **Ruling N (F-S3-1, F-S3-4, F-S3-2, F-S3-8 admin forms).** Event form: `ends_at` must be after `starts_at`, `max_participants` is an integer >= 1 or empty (= unlimited, hint shown); enforced in the Filament form only because events are written nowhere else (factories excepted). Seat form: label unique per event (create and edit, own record ignored) with a German message; the grid bulk-create already skipped existing labels; no unique index on position exists, so none is validated. `EditEvent` builds one header action per target status and evaluates visibility against the live record, so the header is correct right after a transition (tests use `assertActionHidden` instead of `assertActionDoesNotExist`). Filament tables, infolists and date pickers use `d.m.Y` / `d.m.Y H:i` via `configureUsing`, pickers are non-native (German format regardless of browser locale), week starts Monday. *Cost if wrong:* a future second writer for events needs the same rules (move them into an Action then).
- **Ruling O (F-S2-3/4/6/7/8, F-S2-1, teams and participant UI).** Team names are unique case-insensitively: `UniqueTeamName` rule (store, update, Filament) plus the unique index `teams_name_lower_unique` on `lower(name)`; the migration refuses (RuntimeException with the duplicate names and instructions) when duplicates exist instead of deleting anything. Production holds no teams per the prod notes, so this is expected to be a no-op there. A join request notifies the owner (`TeamJoinRequestReceived`) and the answer notifies the requester (`TeamJoinRequestAnswered`), bell only, category `teams`, like Friends: they do NOT consult `NotificationPreferences` (that would add a Teams -> Notifications module edge; there is no preferences UI today). The tournament team picker shows `[TAG] Name`. `/events` has a "Aktuell und kommend" section (announced, registration, live; soonest first, "Zur Anmeldung" while open) above "Vergangene LANs". The 403 page offers the admin link only to orga/admin. Steam/Twitch redirect and callback 404 for unconfigured providers; the connections page lists every provider (`available` flag), a linked account of an unconfigured provider stays unlinkable, unlinked unconfigured ones say "Derzeit nicht verfügbar". Plain team members see "Angemeldet" for their team's entry (`myEntry.isOwner = false`, display only: no check-in/withdraw, no match/report data since those stay owner-only). The confirm-password failure message is translated through `lang/de.json`. *Cost if wrong:* a legitimately duplicate pre-existing team name blocks the migration until renamed; team members cannot act on the entry (only the owner can, as before).
- **Ruling P (F-S3-3/9/10, admin copy and managers).** Relation managers (registrations, tournament entries, linked accounts, food order items) and the disputes page set explicit German model/plural labels and empty states ("Noch keine Anmeldungen" etc.); a script sweep found no other Filament column/filter/field without a label. The registrations manager shows `TicketLabel`, the arrival plan, a status filter and a cancel modal naming the participant; the entries manager offers "Einchecken" only while `CheckInEntry::windowIsOpen()` (new public static, same rule the action enforces). Game form: Pelican egg, default config, presets and the install hint (only consumed by the game-server list) are visible only with `Module::GameServers`; saving a game under core leaves those stored values untouched (EditGame only overwrites them when the module is on). *Cost if wrong:* the install hint is hidden under core although stored; re-enable the module to edit it.
- **Ruling Q (F-S3-5/6/7, notifications, game deletion, QR).** The in-app "Anmeldung offen" invitation moved to the always-registered `Notifications\Listeners\NotifyUsersRegistrationOpen` (the Discord listener now only posts the channel announcement; `RegistrationOpened` moved to the Notifications module, which removed Events -> Discord/Notifications edges and added Notifications -> Events to the architecture baseline). Audience changed from "already-confirmed registrants" (nearly always empty at that moment) to every user without an active registration for the event, minus those who disabled the `registration` category. A game used by tournaments cannot be deleted: model `deleting` guard (`GameInUseException`), Filament delete/bulk actions halt with a German notification, and `tournaments.game_id` is now `restrictOnDelete`. The check-in QR URL is `CheckinUrl::for()` = `APP_URL` + path (modal and print page). *Cost if wrong:* the invitation reaches every account (fine at LAN scale, large communities may want a segment); orga must detach or delete tournaments before deleting a game; APP_URL must be correct in production.
- **Ruling R (tournament status `announced`, drafts invisible).** New `TournamentStatus::Announced` between `draft` and `enrollment` (the column is a plain string, so no migration; no tournaments exist in production). Lifecycle: draft -> (`AnnounceTournament`) announced -> (`OpenTournamentEnrollment`) enrollment -> check_in -> live -> finished; `ReopenToDraft` also takes announced (no entry check needed, sign-up was closed) and still refuses enrollment/check_in with entries. Both Announce and Open run the shared `TournamentSetupCheck`. Decision: "Anmeldung öffnen" is also offered on a draft and performs draft -> enrollment directly (same validation, harmless; it merely skips the announcement). Announced tournaments are visible to every logged-in user (show page now carries game, mode, slots, start and the rules; the new orga form field `rules` feeds it) but sign-up is closed (`TournamentPolicy::enroll` already required `enrollment`) with the hint "Anmeldung öffnet bald". **Behaviour change:** draft tournaments were previously listed with an "Entwurf" badge; they are now invisible to non-orga everywhere: tournaments index/show (`Tournament::scopeVisibleTo`, show 404s), overlays (anonymous, so always 404), Discord `/tournament list|info|checkin|bracket`, the schedule (`SyncTournamentScheduleItem` creates no item for a draft and removes it on return to draft) and the recap tournament count. Tests that relied on draft visibility were changed consciously (`->announced()`). *Cost if wrong:* an orga who wants participants to see "Entwurf" tournaments must announce them instead.
- **Ruling S (withdraw/correct a pending report).** The reporting side (`MatchReport.reported_by`, i.e. the solo user or team owner) can take back or change its claim while the report is `Pending` and the match `Reported`. New `ReportStatus::Withdrawn` (the row is kept, so a late confirm/dispute by the opponent gets the friendly flash "Die Meldung wurde zurückgezogen ..." instead of a 404), `WithdrawMatchReport` (match -> `Ready`) and `CorrectMatchReport` (withdraw + resubmit in one transaction, one `MatchReportUpdated` broadcast), policy ability `withdrawReport` (reporter only, pending only; the Actions re-check identity), routes `matches.report.withdraw|correct`. Both use the match's optimistic `lock_version` and **bump it**: an opponent page still holding the old version fails with the existing `StaleMatchException` toast instead of confirming a claim that was replaced. Correction scores are "own : opponent" like the original report. The orga override is untouched and works on a ready, reported or disputed match. Once the opponent confirmed or disputed, withdrawal is refused (only the orga override remains). *Cost if wrong:* a reporter can retract after the opponent already looked at the score; the opponent only ever commits by confirming.

- **Ruling T (F-S5-1, Q-S5-3, staff notifications queued).** Every notification that mirrors to Discord is `ShouldQueue` (`OrgaPinged`, `CheckinOpened`, `FoodOrderReady`, `MatchReadyBell`, joining the schedule ones): Laravel queues one job per recipient and channel, so the bell (`database`) row lands for every recipient independently and a Discord outage only reaches `failed_jobs`; the "Orga rufen"/"Check-in öffnen"/"Essen fertig" requests can no longer 500 on delivery. Database-only notifications stay synchronous. *Cost if wrong:* the bell rows appear only once a queue worker runs (already required in every profile); with the `sync` driver an outage is still raised inline.
- **Ruling U (Q-S5-2, secondary module navigation).** One sidebar group "Mehr" below the current-event group holds Essensbestellung, Abstimmungen, Mitspieler finden, Dateien and Spielserver, each gated by `useModules().has(...)`, and the event overview mirrors them as buttons; staff additionally get "Infoscreen-Steuerung" (previously an orphan page) in the event group. Vocabulary is unified: "Zeitplan" (not "Programm") and "Abstimmungen" (not "Umfragen") everywhere user-facing, including the Filament nav group and the beamer scene label. *Cost if wrong:* a longer sidebar on full profile; moving an entry is a one-line change in `AppSidebar.vue`.
- **Ruling V (QA round 4 minors).** The gallery ZIP button only shows when approved photos exist and the endpoint answers an empty/failed build with a German toast redirect; OBS overlay pages flag `html.overlay` (root view, by Inertia component name) so the document background is transparent; remote-host addresses must be an RFC 1123 hostname or an IP literal (form and `RegisterHost`); a missing voice installer file is a 404 with a German message; ICS items without an end get an estimated end (tournament 2 h, others 1 h) instead of DTEND = DTSTART; the jukebox page gets a deferred, 20 s cached `musicAvailable` probe (`MusicClient::nowPlaying()`, never throws) and the Music Assistant client has 3 s connect / 10 s total timeouts; buttons, sidebar items/trigger and back links reach 40 px under `pointer-coarse:` only; all file inputs use the shared `FilePicker` (German, native input visually hidden). Q-S5-1 (file allowlist) is kept as is; the CSP browser-report delivery (Q-S7-1) is unverified and untouched. *Cost if wrong:* the ICS estimate is a guess (a real tournament end would need a column); `html.overlay` depends on the `Overlay/` component prefix.

- **Ruling W (pre-LAN security and dependency audit).** `composer audit` and `npm audit` are clean after patch-level updates (Laravel framework, Filament, Livewire, Guzzle, league/commonmark, Flysystem, phpseclib, Symfony components; npm: vite, js-yaml, nanoid, postcss, source-map-js, shell-quote/concurrently). `laravel/wayfinder` and the dev-only `laravel/boost` moved to newer minors/majors because wayfinder 0.1.20 cannot type the HTTP `QUERY` method that the patched framework now reports for `Route::redirect`; boost is a dev dependency and not part of the production image. None of the npm findings was reachable in production: the image only carries the built `public/build`, never `node_modules`. The `docker/discord-gateway` sidecar has no lockfile; its single dependency pin audited clean at the time. Container scan of the built app image reports only base-image (Debian) findings without a fixed version; they resolve through the moving `dunglas/frankenphp` tag on rebuild. *Cost if wrong:* a future audit that flags a transitive dependency of the sidecar is only visible after generating a lockfile; consider committing one.
- **Ruling X (route authorization matrix, throttling stance).** `tests/Feature/Security/RouteAuthorizationMatrixTest.php` derives its expectations from the registered routes: a new unauthenticated route must be added to the public allowlist with a reason, a new authenticated route must be listed as self-service or open-object (or get an IDOR scenario), and id-bearing routes are checked against foreign ids. Rate limits stay as they are (login, passkeys, two-factor, self check-in, CSP reports, orga ping); no per-IP throttle was added to the Discord OAuth callback or to registration, because at a LAN party every guest shares one public address and a per-IP limit would lock legitimate guests out. *Cost if wrong:* the callback can be hit repeatedly; Socialite rejects requests with a bad state before any outbound call, so the exposure is limited to cheap local work.
